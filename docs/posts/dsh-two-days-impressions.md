过去两天，我把主要开发工作流切到了 DSH（DeepSeek Harness）——一个运行在本地的 AI 编码代理框架，通过浏览器 Web 界面操作。我是 Minecraft 插件开发者（AsDuels、DsBorder），AI 成本并存两处：opencode Go 订阅（按用量计）和 DeepSeek API（按余额计），因此在第一天就装了两款插件：`dsh-opencode-usage`（用量/余额监控）与 `dsh-sound-alerts`（任务提示音）。这篇文章从开发者视角，记录这两天的使用体验和两款插件的实际表现。

## 它和聊天工具有本质区别

DSH 不是"对话窗口"，而是一个跑在本机的执行环境：直接读写我的仓库文件、执行 PowerShell 命令、管理后台任务，并能跨多轮持续完成一个长任务。浏览器页面只是入口，真正的读写都发生在本地文件系统上，所有改动都是可审查的 git 变更，而不是对话里的一段代码。

## 与预期不同的几个点

- **Windows 沙箱是真实约束**：只读命令默认运行在 PowerShell 受限语言模式（ConstrainedLanguage），只能用核心 cmdlet；.NET 静态调用、COM、反射等一律不可用，授予写权限后才放开。这要求命令一次写对，否则只能申请更高权限重试。有摩擦，但安全性是实打实的。
- **审批策略按信任阶段调整**：第一天使用 `ask` 模式，每步操作都要确认；观察文件操作无误后，第二天改为 `never`，转为事后通过转录审查。信任建立后，`never` 对效率的提升非常明显。
- **长任务可以真实跑完**：目标（goal）＋任务清单（todo）＋后台任务（background job）的组合，让多步骤任务跨轮持续执行，期间无需人工值守。
- **任务可以委派**：独立任务交给子代理，大规模并行用 workflow 分阶段扇出。计划与执行分离，适合批量审计、迁移这类场景。

## dsh-opencode-usage：用量与余额监控

选择它的直接原因：opencode Go 套餐按用量静默消耗，DeepSeek 按余额静默消耗，两者都在"部署失败时才惊觉额度用尽"。该插件把两者聚合到侧边栏：

- 常驻徽标显示首个已配置 provider 的用量/余额，异常时变红；点击展开详情卡片：各 provider 用量/余额、重置倒计时、历史趋势、告警与 Key 配置。
- 数据源两类：opencode-go 用量（5h 滚动/周/月，官方用量接口）与 DeepSeek 余额（官方余额接口）。Key 解析顺序为环境变量（`OPENCODE_API_KEY` / `DEEPSEEK_API_KEY`）优先，面板配置兜底（明文存于 `~/.dsh/dsh-opencode-usage.json`，权限 0600）。
- 本地历史（`~/.dsh/dsh-opencode-usage-history.json`）支撑突增告警：单次增幅 ≥5%、深夜增长 ≥1%、5h 额度 ≥80% 均触发提醒，余额低于阈值同样告警。对 Key 可能泄露的场景，这类异常检测比"余额归零才发现"可靠得多。
- 采样间隔 5 分钟，历史仅在插件运行期间写入；颜色、字号、阈值、卡片外观均可配置，告警是否影响徽标颜色也可按类别单独开关。

**评价**：把成本可见性嵌入工作流（而非另开一个页面），是这类监控插件最合理的产品形态。扣分项是明文兜底配置与较粗的采样粒度，详见下文。

## dsh-sound-alerts：任务状态的声音反馈

长任务的可用性前提是有可靠的通知渠道。该插件把 DSH 事件映射为不同提示音，经 SSE 推送到 Web 客户端播放（失败时回退轮询），且不阻塞对话：

- 权限/审批就绪 → 双音注意；助手提问 → 三连上行音；回合/命令/工具出错 → 下行警示音；任务正常完成 → 上行完成音。
- 支持全局静音与按类别开关；`sound_alert_status` 可查询静音状态与各类触发计数。

审批改为 `never` 后，实际触发频率最高的是完成音。任务在后台执行期间可以并行处理其他工作，仅靠声音即可区分"继续等待"与"需要处理"——这是长任务工作流最缺的一环。

## 遇到的问题

- **`opencode_usage` 返回值偶发不合法**：使用期间该工具数次返回非法 JSON（`value is not lossless JSON`），疑似插件序列化层 bug，值得向开发者提交 issue。功能可用，但这类偶发错误会破坏可靠性预期。
- **文档以实践探明为主**：workflow/subagent 的 API 边界与沙箱规则目前主要靠试错确认，正式文档覆盖不足。
- **采样粒度 5 分钟**：徽标与真实数值存在分钟级滞后。对余额型数据可接受，对用量型（5h 窗口）略微偏粗。

## 小结

两天不足以盖棺定论，但方向已经清楚：DSH 的价值在于把"与 AI 对话"变成"在真实仓库中与 AI 协作"，插件机制则是它的核心扩展点——上述两款插件分别解决成本感知与异步任务感知两类问题，且都不用离开主工作流。后续计划是继续使用，并向 `dsh-opencode-usage` 提交上述序列化问题的 issue。
